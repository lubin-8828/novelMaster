## 1. 目标

一个人用的 AI 辅助小说写作工具，跑在命令行里，用类 TUI 的交互方式驱动一条完整写作流水线：

**想法 → 大纲 → 事件推演 → 章节大纲 → 正文 → 审查 → 去 AI 味 → 用户验收 → 资料回填 → 清空上下文 → 下一章**

一句话版本：**把"写小说"这件脑子里的事，变成一条有持久化状态、可回退、每步都要用户拍板的流水线。**

核心设计取向（用户明确要的）：
- 每章的 AI 记忆用完即弃。章末清空，下一章重建上下文，杜绝脏上下文。
- 每一步都要用户确认，AI 不能自作主张往下走。
- 审查必须有据可查 —— 对着设定集、人物档案、前文说话，不能凭感觉。

## 2. 成功判据

**由用户主观判断，不设客观指标。** ✅用户 2026-09-21 明确。

具体落法：唯一判据就是**用户检查通过**（每章一次）。工具不提供"质量分""合格线"这类自动结论 —— 审查与去 AI 味只负责把**证据摊开**（问题条目 + 依据引用 + 改前改后对照），拍板权 100% 在用户手上。

这条也解释了为什么"有据可查"是硬要求：既然没有客观判据，AI 就必须交出可核查的依据，而不是交一个结论。

## 3. 背景与动机

- 用户已有明确的写作流程直觉，需要一个承载它的工具，而不是通用 AI 聊天窗口。
- 通用聊天窗口的三个致命问题：上下文越滚越脏、记不住人物和设定、长篇之后前后矛盾。本方案的设计正是逐条对冲这三点。

## 4. 受众 / 使用者

- 只有用户本人。单人单机，无并发、无权限、无协作。
- 这意味着可以放弃所有多用户相关的设计成本。

## 5. 范围边界

**做（第一版）：**
- 单本小说，全链路打通（想法 / 设定 / 人物 / 大纲 / 事件 / 章节 / 正文 / 审查 / 去 AI 味 / 验收 / 回填）
- 分层命令式 TUI 交互
- 全部资料落盘持久化
- 正文产出为 **纯 txt，不使用 markdown 语法**
- 多 agent 用于大纲讨论、逻辑校验、剧情头脑风暴（脑暴需用户先给方向）

**不做（明确排除）：**
- 多本小说切换与管理 ← 用户明确确认第一版不做（⚠️但目录结构需按"每本小说一个根目录"设计，为第二版留位）
- 云同步、账号、多人协作
- 富文本编辑器、所见即所得排版
- epub / docx 等格式化导出
- 自动生成本章大纲而不经用户输入（违背"每步要确认"）
- 未经用户给定方向的自动剧情脑暴

## 6. 现有基础与依赖

- **语言**：TypeScript（✅用户指定）
- **交互**：命令行 / 类 TUI（✅用户指定）
- **AI 能力**：`@earendil-works/pi-coding-agent`（pi agent SDK）（✅用户指定）
  - 已确认 SDK 能力：`createAgentSession()` 创建独立会话；`SessionManager.inMemory()` 纯内存会话（正是"用完即弃"需要的）；`AgentSessionRuntime` 支持 new-session / 会话替换；`compact()` 支持压缩；TUI 组件来自 `@earendil-works/pi-tui`。
- **去 AI 味能力**：复用用户本地已有的 `humanizer` skill（✅用户指定）。该 skill 提供 25 条编号模式（§1–§25，按强度排序：§1–§5 单次命中即可动，标注 *weak alone* 的需多条同时命中），**这些编号天然构成可引用的依据坐标系**。它同时规定了输出形态（命中清单 + 改稿 + 最终稿），正好满足"有据可查"。
  - 关键接口：该 skill 规定「用户给文风样本时优先匹配样本，样本覆盖通用模式规则（含破折号规则）」。→ **本书已写章节就是最合适的文风样本**，这是让去 AI 味贴合本书文风而非通用腔的天然钩子。
  - 该 skill 明确「虚构作品豁免『不得添加事实』」—— 与本项目性质一致。
- **模型**：读取 pi 自身配置（`~/.pi/agent/settings.json` 的 `defaultProvider` / `defaultModel`），不硬编码。用户当前默认 = `deepseek` / `deepseek-flash`。
- 从零开始，无既有代码。
- **详细设计文档**：根文档 `DESIGN.md` + 子文档 `docs/design/*.md`（v1，2026-09-21）。本方案是"要什么"，设计文档是"怎么做"；两者冲突时以设计文档为准（它晚于本方案且经过 API 核对）。

## 7. 约束

- 单机、单用户、无服务端。
- 正文严格 txt 纯文本，禁止 markdown 语法（`#`、`**`、`- ` 列表等）。
- 每章的上下文必须自包含 —— 因为会话是新建的，不存在跨章记忆，一切依据都必须能从磁盘读出来。
- 模型：读 pi 自身配置，且**支持按用途覆盖**（正文可用强模型，脑暴/校验用默认）。自用工具，不设成本上限。✅已确认

## 8. 关键假设与前提

- ⚠️假设：**"清空记忆" = 每章新建一个 `AgentSession`**，而不是在同一会话内做压缩或重置。理由：这是语义最干净、也最符合用户描述的实现。章末调用 `runtime.newSession()`。
- ⚠️假设：**多 agent = N 个独立 `AgentSession`，各带不同角色 system prompt，跑完由父层综合**。SDK 没有内建的多 agent 概念，这是最简且可控的路径；角色之间不互相投票，只提供独立视角，由父层归纳共识与分歧。
- ✅已确认（随 §10.1 目录规格一并通过）：**"不使用 markdown 语法"只约束正文**。大纲、设定、人物档案、审查报告属于"工作资料"而非"正式文章"，用 markdown/json 以便结构化与引用 —— 这是审查能"有据可查"的前提。
- ⚠️假设：**审查依据 = 结构化落盘的设定集 + 人物档案 + 人物关系 + 前文**。没有结构化的"设定"就没有"依据可查"，所以设定必须是可检索、可引用的数据，而不是一句描述。
- ⚠️假设：**去 AI 味也需要一份可检验的规则清单**（复用 humanizer 思路），否则同样会沦为"凭感觉"。
- ⚠️假设：事件→章节是**一对多**，章节必须挂在某个事件下（✅用户说过一个事件可以写很多章）。

## 9. 方案选项与取舍

| 选项 | 做法 | 优点 | 代价/风险 | 结论 |
|------|------|------|-----------|------|
| 上下文 A | 全书大纲 + 事件 + 人物档案 + 设定集 + **最近 5 章全文** + 更早章节滚动摘要 + 本章大纲 | 忠实且有界，长篇不失控 | 需要额外维护"章节摘要"这一持久化产物 | ✅已采纳（用户定：最近 5 章） |
| 上下文 B | 注入全部已写章节全文 | 实现最简单，完全忠实 | 第 50 章时 token 与成本失控，且重点被稀释 | ❌排除 |
| 上下文 C | 只注入摘要，不注入原文 | 最省 | 丢失文风、称呼、细节连续性，直接影响下一章质量 | ❌排除 |
| 多 agent | 多个独立 AgentSession + 角色 prompt，父层综合 | 简单、成本可预期、视角互不污染 | 无真正的"互相反驳"过程 | ✅采纳 |
| 多 agent | 引入子 agent 委派链路 | 支持多轮交互式辩论 | 复杂度、成本、可调试性都陡增 | ❌第一版排除 |
| 审查依据 | 结构化设定集 + 人物档案，报告逐条引用 | 可追溯，符合"不能凭感觉" | 前期要把设定整理成结构化数据 | ✅采纳 |
| 审查依据 | 每次审查时让 AI 现读前文自行判断 | 免维护 | 无法追溯，判定不稳定 | ❌排除 |

## 10. 推荐方案

### 10.1 持久层设计（详细规格）

**目录树**

```
<小说根目录>/
├── meta.json                  # 小说元信息（覆盖式）
├── state.json                 # 进度指针 + 章状态机（覆盖式，唯一真相）
├── inbox.md                   # 想法收集箱（追加式）
├── outline.md                 # 故事主线大纲（覆盖式 + 底部修订记录）
├── setting/
│   ├── index.json             # 设定条目索引（每条有稳定 ID）
│   └── S-001.md ...           # 条目详述 + 修订记录（追加式）
├── characters/
│   ├── index.json             # 人物索引（静态档案 + 当前状态）
│   └── C-001.md ...           # 人物详述 + 关键事件时间轴（追加式）
├── relations.json             # 人物关系（当前状态 + 追加式 history）
├── events/
│   ├── index.json             # 事件列表（标题/状态/阶段/关联章/依赖）
│   └── E-001.md ...           # 事件当前描述 + 细化历史（追加式）
├── chapters/
│   ├── index.json             # 章节索引（标题/挂靠事件/状态/字数）
│   ├── 012.txt                # 正文：纯文本无 markdown ← 唯一受此约束的文件
│   ├── 012.outline.md         # 本章大纲（用户确认版）
│   ├── 012.summary.md         # 本章摘要（供后续注入）
│   ├── 012.review.md          # 审查报告
│   ├── 012.deai.md            # 去 AI 味报告
│   └── 012.reflow.md          # 资料回填报告（结章闸门凭证）
└── logs/                      # 会话与操作留痕（只增不改）
```

**四条设计原则**（每条都对应一个「不这么做就会坏」）

1. **可被引用的东西必须有稳定 ID。** 审查要说"这里违背了设定 S-001"，而不是"这里违背了设定"。没有 ID，"有据可查"就退化成"AI 说它对"。所以设定与人物都索引化，ID 一经分配**永不复用**（即使条目被废弃）。
2. **追加式与覆盖式必须分开。** 人物时间轴、事件细化历史、关系变更史、inbox、logs 是追加式（只增不改）—— 它们是**历史**，改写历史等于伪造依据。大纲、设定条目正文、元信息是覆盖式 —— 它们是**当前结论**。`reflow.md` 的存在意义就是记录每次回填往追加式文件里写了什么。
3. **正文文件里只有正文。** 章节号、标题、状态全部放 `index.json`。理由：你要亲手编辑 txt，任何混进正文的元数据都会在你编辑时被误删或误改。
4. **`state.json` 是唯一进度真相。** 章节状态只在这里，不在别处重复记录；多源真相 = 迟早不一致。

**关键字段**

`meta.json`
```json
{
  "schemaVersion": 1,
  "title": "",
  "genre": [],
  "premise": "用户最初的想法原文（不改写，作为一切推断的根）",
  "logline": "整理后的一句话简介（可反复修改）",
  "pov": "第三人称限知",
  "tense": "过去时"
}
```
`pov` / `tense` 不是装饰：审查项 F3（视角越界）和 G2（人称时态漂移）要靠它判定。

`state.json`
```json
{
  "schemaVersion": 1,
  "currentChapter": 12,
  "currentEventId": "E-003",
  "chapterStatus": "awaiting_user_review",
  "pendingReflow": false
}
```
章状态机（正向线性推进，回退只能由用户触发）：
```
not_started
  → outlined             用户确认本章大纲
  → drafted              正文生成
  → auto_reviewed        自动审查完成
  → deai_done            自动去 AI 味完成
  → awaiting_user_review ← 交给用户（循环点）
      ├→ user_edited → reflowed    用户自改后 AI 已回填
      └→ ai_revised  → 回到 auto_reviewed
  → accepted             /done 通过，随后清空上下文
```
`/done` 的**准入条件**：`chapterStatus == reflowed` 且 `pendingReflow == false`。未回填不许结章 —— 把"资料可信"变成代码约束，而不是靠自觉。

`setting/index.json` 条目字段：`id` / `name` / `category`(world_rule|location|faction|item|taboo|custom) / `summary` / `establishedIn`(首次确立于第几章，0=设定期) / `tags`。
`S-001.md` 正文 = 详述 + 追加式修订记录（谁在第几章改了什么）。

`characters/index.json` 条目字段：`id` / `name` / `aliases[]` / `role`(protagonist|antagonist|supporting|minor) / `firstAppeared` / `status`(alive|dead|missing|unknown) / `lastUpdatedChapter` / `static`(年龄、外貌、背景、性格、说话习惯、目标、恐惧)。
`C-001.md` 正文 = 档案详述 + **追加式关键事件时间轴**：
```
## 关键事件时间轴
- [CH-001] 在码头发现异常货箱。
- [CH-007] 向张局汇报，被要求组建研究团队。
```
`lastUpdatedChapter` 不是冗余：它让回填步骤能发现"这个角色已经 8 章没更新过了"，把遗漏从"靠记性"变成"可检测"。

`relations.json` —— 关系是有历史的（敌 → 友 → 决裂），所以每条关系 = **当前状态 + 追加式 history**：
```json
{ "id": "R-001", "from": "C-001", "to": "C-002", "type": "subordinate",
  "directed": true, "status": "active", "since": 1,
  "history": [ { "chapter": 7, "change": "改为直接向张局汇报，绕过科长" } ] }
```

`events/index.json` 条目字段：`id` / `title` / `stage` / `status`(planned|in_progress|done|abandoned) / `order` / `chapters[]` / `dependsOn[]` / `leadsTo[]` / `origin`(ai_proposed|user_specified|foreshadow)。

**伏笔复用事件结构**（✅ 2026-09-21 定）：伏笔就是一个 `origin: foreshadow` 的事件 —— `status: planned` 表示已埋未收，`done` 表示已回收；另带 `plantedIn`（埋设章节）与 `payoffExpectedAt`（预计回收章节，可空）。
这么定的收益：审查项 E2 不需要任何新数据结构，只要筛 `origin == foreshadow && status == planned`、按 `payoffExpectedAt` 排序，就能输出"到本章为止还挂着的伏笔"。伏笔也不再是特殊公民 —— 它和普通事件一样进"细化历史"、一样受 D3 进度检查覆盖。
`E-003.md` = **当前描述 + 追加式细化历史**，直接对应你举的例子：
```
## 当前描述
李明发现问题并汇报给上级，上级要求组织研究团队确认事件真实性和威胁等级。

## 细化历史
- [CH-011] 确认事态真实性和严重等级、可信程度
- [CH-012] 填充为：李明发现问题并汇报给上级，上级要求组织研究团队确认事件真实性和威胁等级

## 涉及
人物 C-001 李明、C-002 张局 ／ 设定 S-001 ／ 章节 CH-011, CH-012
```
"当前描述"始终是最新最细的版本，"细化历史"保证每次填充都能回看。审查项 D3（事件进度倒挂）就是拿正文去比"当前描述"。

`chapters/index.json` 条目字段：`no` / `title` / `eventIds[]`（可多个）/ `primaryEventId`（主事件） / `status` / `wordCount` / `createdAt` / `acceptedAt` / `revisionCount`。

**一章可跨多个事件，但必须有主事件**（✅2026-09-21 定）：真实写作里常见"推进主事件 + 回收一个伏笔"或"收尾旧事件 + 铺垫新事件"，硬限制成一章一事件会逼你在无关的地方切章。但主次必须分明 —— `primaryEventId` 就是 §10.3 第 4 项"当前事件全文"的取数依据，没有它装配器不知道该注入哪条。

**落盘校验**：正文写盘时检查行首 `#`、`**`、`>`、反引号等 markdown 标记，命中就提示你确认。只提示不阻断 —— 小说正文里出现 `-` 是合法的，硬拦会误伤。

### 10.2 交互层：分层命令 + 层内自然语言

```
顶层：/help  /setting  /person  /outline  /event  /write  ( /novel 第二版 )  /quit
──────────────────────────────────────────────────────────────
/setting  世界观设定集管理
/person   人物档案与人物关系管理
/outline  故事主线大纲：交互式创建/讨论/修改；可触发多 agent 讨论与逻辑校验
/event    事件推演与填充：新建/推演/确认/关联章节；可触发定向脑暴（须用户先给方向）
/write    写作模式
  ├─ /next     推演下一章大纲，交用户确认
  ├─ /context  打印"本章上下文包"（这一章到底喂给 AI 了什么）
  ├─ /review   审查（自动触发，也可手动补跑）
  ├─ /deai     去 AI 味（自动触发，也可手动补跑）
  ├─ /done     验收通过：落盘 + 回填资料 + 清空上下文
  └─ /quit     退出写作模式
```

层内规则：进入某一层后直接自然语言跟 AI 对话（对话即操作）；`/help` 显示当前层可用命令；`/quit` 退回上一层。

设计理由（为什么值得独立分层）：设定的核对频率远高于大纲重写，人物档案会被每一章回填 —— 如果全部塞进 `/outline`，用户每次改一条人物关系都要穿过大纲的全部上下文。分层让 AI 在每层只装载该层的数据，既省 token 也让行为更可预期。

### 10.3 上下文装配器（字段级规则）

每章新建会话时，按**固定顺序**装配上下文包。顺序原则：从最稳定排到最易变，最"当下"的放最后。

| # | 内容 | 取数规则 | 理由 |
|---|------|----------|------|
| 1 | meta 摘要 | `title` / `genre` / `premise` / `logline` / `pov` / `tense`，全量 | "这本书是什么"的最小锚点，成本极低 |
| 2 | `outline.md` | 全文 | 只有一份，且是判断本章是否脱轨的基准；省了它 AI 只能看局部 |
| 3 | 设定 | **双层**：全部条目的 `summary` + 相关条目全文 | 设定越写越多，全量全文会淹没重点；只给相关的又会让 AI 编新设定（A2） |
| 4 | 当前事件 | 挂靠事件的全文（当前描述 + 细化历史） | 本章要推进的就是这个对象 |
| 5 | 相关人物 | 静态档案 + **全量**关键事件时间轴 | 时间轴条目短，截断会让 AI 以为早期经历没发生过 |
| 6 | 相关人物关系 | 仅**两端都在相关人物集合内**的关系 | 只提一端的关系是无效信息 |
| 7 | 最近 N 章正文（**N 可配置，默认 5**） | `chapters/(N-5..N-1).txt` 顺序全文 | 唯一注入原文正文的部分，是连续性最主要的来源（也是成本主项，故做成可配置） |
| 8 | 更早章节摘要 | `chapters/1..N-6.summary.md` 顺序 | 长篇不失忆的代价就是这个 |
| 9 | 本章大纲 | `NNN.outline.md`（用户确认版） | 放最后：当下任务最不该被忽略 |

**"相关"的判定规则**（第 3、5、6 项用）：

```
相关人物 = 本章大纲标注的 characterIds
         ∪ 当前事件涉及的涉及人物
         ∪ 最近 5 章出场人物

相关设定 = 本章大纲标注的 settingIds
         ∪ 当前事件涉及的设定
         ∪ 最近 5 章中出现过的设定
```

全部取并集，不取交集。理由：宁可多喂一条人物档案，也不要因为 AI 不知道某个人物而写出矛盾 —— 而当发现真喂多了，代价只是一次成本调整。

**顺序里的一个实际收益**：第 1–6 项在相邻章节之间几乎不变，只有 7–9 项会变。把稳定部分放前面，就是可命中的 prompt 缓存前缀 —— 在每章都要重建上下文的架构下，这不是小优化：**缓存命中的是占比最大的那部分**。

**必须可打印**：`/context` 输出每一部分的估算 token 数与实际内容。理由：成本主项是第 7 项（5 章正文），你得能一眼看到"这章上下文多大"，才能决定要不要把 5 调小。看不见的东西调不动。

### 10.4 单章闭环

```
/next  →  AI 按当前进展 + 前文推演本章大纲  →  用户确认（可多轮修改）
   ↓
开写（新会话 + 装配上下文）
   ↓
自动 /review：对照设定集/人物档案/关系/大纲/前文，输出逐条带引用的报告
   ↓
自动 /deai：按 AI 味规则清单改写
   ↓
用户检查（可手动补跑 /review、/deai）
   ↓
修改：用户自己改 txt  ∨  让 AI 改
   ↓
用户改完 → 告知 AI → AI 回填资料（人物档案追加、关系更新、事件填充、章节摘要、事件进度）
   ↓
/done 验收通过 → 落盘 txt → 清空上下文 → 明确告知已清空 → 询问是否写下一章
```

### 10.5 多 agent 的边界

- 用途：大纲讨论、逻辑校验、剧情头脑风暴。
- 脑暴**必须**由用户先给出一个想法/方向才启动（✅用户明确要求），否则容易偏离用户思路。
- 角色按话题自适应生成，不写死固定角色表。
- 父层负责综合：共识、真实分歧、被忽略的选项、新暴露的假设 —— 不由 agent 互相投票。

### 10.6 去 AI 味（复用 humanizer）

三步走，每步留痕：

1. **标记** —— AI 通读本章，按 humanizer 的 25 条模式由强到弱标记命中位置，输出「模式编号 + 原文片段」清单。
2. **改写** —— 以**本书已写章节**作为 voice sample（humanizer 规定样本优先于通用规则），产出改稿。
3. **复检** —— 走 skill 的第 3 步，专查最容易漏网的五类：not-X-but-Y 对比、单句收尾、破折号、三段式排比、加粗标签。

产出物 `chapters/NNN.deai.md`，固定三节：「命中清单 / 改前 / 改后」。**"命中清单"单独成节**（✅2026-09-21 定）：你的核对动作是"逐条检查它标的对不对"，所以它必须是一份能从上往下划勾的清单，而不是一段说明文字。

**为什么这么设计**：用户要求"不能凭感觉"。humanizer 的模式编号提供了可引用的坐标系（"这里命中了 §8 破折号滥用"比"感觉有点 AI"有用得多）；而"样本优先"条款把它锚到本书自己的文风上，避免改到最后变成另一种通用腔。

**为什么它天然适合本项目**：去 AI 味的对象是小说，而 humanizer 是通用散文工具，两者最容易冲突的地方是它要求"不得添加事实"。skill 自己已经豁免了虚构作品，所以不需要改造，直接复用。

### 10.7 审查规则清单

**架构前提：审查者不修改稿子。** 审查是只读的一次性 agent，只出报告。两个理由：让写手自查自己的稿子必然有确认偏差；一旦允许它顺手改，"哪一版是被审查过的"就说不清了。修改是另一条独立的线（你改，或你指挥 AI 改）。

**三个审查员并行，父层合并去重**（对应你说的"多 agent 检查、逻辑校验"）：
- 设定审查员（A 类）
- 人物与关系审查员（B、C 类）
- 逻辑与叙事审查员（D、E、F、G 类）

**依据引用格式**（可查性的落点）：`文件#条目ID` 或 `chapters/003.txt:第2段`。
例：`依据：setting/index.json#S-001`、`依据：characters/C-001.md 时间轴[CH-005]`。

**严重度三级**：`blocking` 必须处理 ／ `warning` 建议处理 ／ `note` 供参考。你要逐条拍板，所以 blocking 必须排在最前。

**条目粒度 = 段落级**（✅2026-09-21 定）：一条问题对应一个段落。理由：你要逐条拍板，段落级才能让你精确定位到"改这一句"；区块级（整个场景）会让你面对一条问题却不知道该动哪儿。代价是条目变多，由三级严重度压住（blocking 通常很少）。

**检查项**

A. 设定一致性（依据 `setting/`）
- A1 世界规则违背 —— 正文中的现象或能力与某条 world_rule 冲突
- A2 设定未确立就用 —— 正文引入了 setting 中不存在的规则/组织/地点/术语。判定：补设条目，还是删掉这个表述
- A3 设定漂移 —— 正文实际改写了已有设定，但条目未更新（转成回填任务或修订建议）
- A4 禁忌被忽略 —— 设定里的 taboo/限制被角色轻易绕过

B. 人物一致性（依据 `characters/`）
- B1 性格偏离 —— 行为与档案的 personality/说话习惯 不符
- B2 能力越界 —— 角色用了档案中不具备的能力
- B3 信息越界 —— 角色知道了以他的位置不可能知道的信息（悬疑／推理的命脉）
- B4 状态错误 —— 已死、失踪、重伤的角色照常活动
- B5 称谓不一致 —— 同一角色被不同称呼，需区分"有意"与"笔误"
- B6 目标漂移 —— 行为与 goal/fear 冲突，且正文没有交代转变

C. 关系一致性（依据 `relations.json`）
- C1 关系状态不符 —— 已决裂却仍以旧方式相处
- C2 亲疏与称呼不匹配 —— 称呼的亲密程度与关系类型矛盾
- C3 关系变化未留痕 —— 正文里关系变了，但 history 没有对应记录

D. 时间线与因果（依据 `events/`、`chapters/`、前文）
- D1 时间矛盾 —— 季节、昼夜、时长、"三天前"与实际章节间隔对不上
- D2 因果断裂 —— 事件发生缺少前置条件（`dependsOn` 里的前置事件还没发生）
- D3 事件进度倒挂 —— 正文内容超出或倒退于事件的"当前描述"
- D4 行程不合理 —— 两地距离与耗时对不上

E. 剧情与大纲（依据 `outline.md`、`events/`）
- E1 主线脱轨 —— 本章与所在阶段目标无关联
- E2 伏笔未回收 —— 筛 `origin == foreshadow && status == planned`，按 `payoffExpectedAt` 排序输出"还挂着的伏笔"（机制见 §10.1）
- E3 情节重复 —— 本章事件与前面某章高度相似

F. 逻辑与叙事（依据本章正文 + 前文）
- F1 情节漏洞 —— 角色本可轻易解决的问题被绕开
- F2 动机不足 —— 关键决定缺少铺垫
- F3 视角越界 —— 与 `meta.json` 的 pov 冲突（如限知视角却写了别人的心理）
- F4 信息冗余 —— 重复交代前文已充分建立的信息
- F5 场景内物理逻辑 —— 同一场景里位置、人数、物件前后不一致

G. 硬性规范（依据本项目规则）
- G1 正文含 markdown 语法
- G2 人称／时态漂移 —— 对照 `meta.json` 的 pov/tense
- G3 章节字数异常 —— 相对本书均值偏离过大（弱提示）

**报告格式**（`chapters/NNN.review.md`）
```
## 摘要
blocking 2 条 / warning 4 条 / note 1 条

## blocking
### [A2] 设定未确立就用
- 位置：第 3 段
- 现象：出现"共鸣场"，setting 中无对应条目
- 依据：setting/index.json（检索无命中）
- 建议：补设条目，或删去该表述

### [D3] 事件进度倒挂
- 位置：第 17 段
- 现象：正文出现"研究团队已确认"，但 E-003 当前描述仍是"上级要求组建团队"
- 依据：events/E-003.md 当前描述 ／ chapters/012.txt:第17段
- 建议：调低正文进度，或把这次推进作为事件填充正式写入
```

**为什么审查在前、去 AI 味在后**：审查改的是**事实层**（对不对），去 AI 味改的是**表达层**（像不像人写的）。顺序反了的话，去 AI 味改过的句子再被判有问题，那一轮改写就白做了。

**为什么检查项要写死成清单**：用户把成功判据说成"我判断"。那 AI 唯一能做的就是**不许自由发挥** —— 每次审查都跑同一份清单，你才能对比"这一章和上一章的审查结果"，也才能发现清单本身缺了什么、然后去补。让 AI 每次凭理解去审，你连它漏了什么都不知道。

## 11. 执行步骤 / 里程碑

1. **骨架** —— 项目脚手架、TUI 外壳、分层命令路由（`/help` `/quit` 先跑通）、小说根目录初始化。
2. **资料层** —— `/setting`、`/person`（含人物关系）跑通，结构化读写 + 人工可读。
3. **大纲层** —— `/outline` 交互式建立主线大纲 + 多 agent 讨论/逻辑校验。
4. **事件层** —— `/event` 事件推演、确认、用户自指定、事件→章节的关联。
5. **写作层最小闭环** —— `/write` + `/next` + 上下文装配器 + 生成正文。
6. **质量层** —— `/review`（带引用）+ `/deai`（规则清单）+ 报告落盘。
7. **回填与清空** —— 资料回填、章节摘要生成、`/done` 清空上下文并通知。
8. **多 agent 脑暴** —— 定向剧情脑暴（需用户给方向）。

顺序理由：先做资料层是因为**审查的依据来自资料层**；审查做不出来，写作闭环就不成立。多 agent 放最后是因为它不阻塞主链路。

## 12. 风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| 审查沦为"凭感觉"（无法引用依据） | 高 | 高 | 资料层必须先结构化；审查报告强制逐条引用条目 ID / 章节位置 |
| 摘要在长篇累积中失真，导致后面章节跑偏 | 高 | 高 | 摘要只做压缩不做改写；保留"最近 5 章全文"作纠偏锚点；摘要生成后允许用户抽查修正 |
| 上下文装配过载（塞太多重点被稀释） | 中 | 中 | 装配器可打印检查；按需只注入"相关人物"而非全部人物 |
| 多 agent 成本失控 | 中 | 中 | 严格限定触发条件（脑暴必须用户给方向）；默认角色数固定 |
| 默认模型（deepseek-flash）撑不起长篇小说正文质量 | 中 | 高 | ✅已定：支持按用途分别指定模型 —— 正文用强模型，脑暴/校验用 pi 默认 |
| 去 AI 味改完反而丢掉作者的文风与特异细节 | 中 | 中 | humanizer 自带"保留作者声音"清单（特异细节、未解的张力、年代感用词、真正的自我修正）；强制以本书前文为样本 |
| 资料回填遗漏，导致后文依据失真 | 中 | 高 | 回填作为 `/done` 的**前置条件**，未回填不允许结束本章 |
| 用户自己改 txt 后 AI 不知道 | 中 | 中 | 用户改完主动通知 AI 触发回填（✅用户已定此流程）；回填时以磁盘内容为准 |
| TUI 交互复杂度超出预期 | 中 | 中 | 先做线性问答式，再做富交互；不追求花哨 |
