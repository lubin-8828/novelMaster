# decisions — 关键设计决策与原因

> 父文档：[`DESIGN.md`](../../DESIGN.md)
>
> **本文档是动手前的必读项。** 下面每一条都是已经权衡过的决策；不了解「为什么」就改动，很可能把它退回到已经被否决的形态。

## 1. 决策 → 根因

| 决策 | 根因（为什么非这样不可） |
|------|--------------------------|
| **宿主式架构，不自研 TUI** | 价值在数据层 / 上下文装配器 / 审查规则三处，不在终端渲染。pi-tui 只提供零件，不提供「编辑器 + 对话 + 流式 + 会话管理」那一整层；自研等于重写 pi 已有的 80%，还要跟着 pi 升级 |
| **结构化数据只经 custom tools 写入** | JSON 被 LLM 手写必然漂移（字段名变体、漏 `schemaVersion`、数组变对象）。而所有审查依据都建立在这些文件上 —— 依据链是承重墙，结构一坏就断 |
| **追加式与覆盖式分离** | 历史可改 = 依据可伪造。用户之所以敢信审查，是因为它能指着「CH-005 那章发生了这件事」说话；这条记录若能被后续回填悄悄覆盖，整个依据链就烂了 |
| **审查者只读（连改的能力都没有）** | ① 写手自查自己的稿子有确认偏差；② 一旦允许顺手改，「哪一版是被审查过的」就说不清了 —— 而用户的验收对象必须是确定的 |
| **结构化提交（工具参数）而非 JSON 文本** | 模型可以写出一段「看起来像 JSON 的散文」骗过解析器，但骗不过 typebox schema。这直接决定了审查报告能不能被机械汇总与校验 |
| **依据引用可校验** | 不存在的依据 = 幻觉。能自动识别出来，才不会要求用户去人工核对每条引用是否真实 |
| **不做 LLM 汇总层** | 审查条目已经是结构化的，机械合并足够；多一层 LLM 只会引入新的编造风险 —— 而编造正是这套机制要防的东西 |
| **冲突条目两条都保留** | 两个独立视角矛盾这件事本身就是高价值信号；机械取一方会把它抹平。同一条理由也适用于脑暴不投票 |
| **脑暴父层综合、不投票** | 投票式少数服从多数会掩盖真实分歧，而分歧是用户最需要看到的东西 |
| **脑暴必须先有用户给定的方向** | 没有方向的自由发散容易偏离用户思路；用户要的是「在我指的方向上帮我展开」，不是「换一个故事」 |
| **审查在前、去 AI 味在后** | 审查改事实层（对不对），去 AI 味改表达层（像不像人写的）。反了的话，去 AI 味改过的句子再被判有问题，那一轮改写白做 |
| **humanizer 显式注入而非 skill 自主加载** | 「做没做去 AI 味」必须是代码事实，不能是模型的心情。skill 自主加载是模型驱动的 —— 这章想不起来加载就静默跳过了，而用户从结果上分辨不出 |
| **检查清单写死 28 项，不让 AI 自由审** | 成功判据是「用户判断」，所以 AI 唯一能做的是不许自由发挥。跑同一份清单，用户才能横向对比、才能发现清单缺了什么 |
| **依据引用取并集不取交集** | 两种错误的代价不对称：多喂一条人物档案只是多点 token，漏一条会导致一致性事故，而一致性事故要靠用户逐条审出来 |
| **失败不静默降级** | 用户判断是最终判据，假信号会让整套设计失效 |
| **`state.json` 是唯一进度真相** | 多源真相迟早不一致，而不一致时没有任何依据可以裁决哪个是对的 |
| **`/done` 有准入闸门（未回填不许结章）** | 成功判据由用户主观判断 → AI 必须摊开证据而非给结论 → 用户判断建立在资料层可信之上。资料一失真，判断就建立在假信息上 |
| **正文文件里只有正文** | 用户要亲手编辑 txt；任何混进正文的元数据都会在编辑时被误删或误改 |
| **原计划的输入拦截层被删除** | 层面本就是进程内变量，`before_agent_start` 直接读即可。把同一个信息先写进输入文本再读出来是纯粹的中间环节，只增加出错面 |
| **命令表拆成两张** | 否则跨层命令被重复注册、被 pi 后缀化成 `/brainstorm:1`（见「踩坑记录」） |
| **未实现的命令也注册** | 只在 `/help` 列出却不注册，敲下去会被当成普通文本交给 AI —— 用户以为执行了命令，实际是 AI 在揣摩他的意思 |
| **无构建步骤（Node 原生类型剥离）** | 少一层构建就少一层「源码与运行物不一致」的可能，也少一套「改完忘了重新构建」的失败模式 |
| **不引入数据库 / ORM / TUI 框架** | 单机单用户，JSON + txt 足够，且用户明确要求资料可读可改 |
| **数据结构只有 typebox 一份定义，TS 类型靠 `Static<>` 推导** | 手写 interface 与 typebox 两套并存 = 同一个事实的两个副本，而两者一旦漂移，症状是「类型检查说合法、运行时校验说非法」这种最难查的形态 |
| **护栏只拦 write/edit，不动 shell** | 关 shell 能堵住「用 bash 手写 JSON」这条旁路，但代价（AI 不能跑 git / 查日志 / 跑测试）是立刻发生的；而那条旁路需要模型主动绕开一个明确的拒绝提示，不是它被拦住后的自然行为。护栏的作用是把正常路径摆正，不是穷举所有绕法 |
| **正文校验用两段式（先不写、确认后重调）** | 工具是单次调用，没有二次交互能力。先写再提示等于「阻断无效」—— 文件已经写坏了，提示只是事后通知 |
| **追加式写入用子序列断言，不用行数比对** | 行数不减是无效校验：删一行加一行也能保持行数不变，而那正是最需要被抓住的偷改 |
| **一次 upsert 写两个文件时，先详述 md 再索引 json** | 两个方向的后果不对称：孤儿 md 无害且下次可覆写，坏引用（索引有、文件无）会让审查报告引用一个不存在的东西，依据链当场断 |
| **同状态的状态转移也拒绝** | 状态转移是一条边，不是「设为某值」。同状态重复转移说明调用方逻辑有误，静默成功会把这个 bug 藏起来 |
| **层面清单全量注入，不设条数上限** | 每条 `id + name + summary` 约 30 token，100 条才 3k；截断省下的 token 很少，代价却是 AI 不知道某条目存在 → 编一条重复的。省 token 应该压字段，不是减条目 |
| **资料层的改动只转述 diff，不设阻断式确认** | 改动是用户自己发起的，不是 AI 自主决定；阻断会强制 LLM 再调一次工具。与正文校验的区别在于「谁发起的改动」，不在于改动大小 |
| **层面数据不走上下文装配器** | 装配器是为「生成一章正文」服务的重型设施；层面装载只需读索引 + 渲染。让它多一个与写作无关的调用者，只会为它引入不必要的复杂度 |
| **唯一的例外：`/write` 层注入完整上下文包** | 这一层每回合都可能是「写吧」，而 `before_agent_start` 无法预知哪一句是（也不应该猜）。代价是每句话带几万 token —— 用「干完就走」的使用方式对冲（层规则里写明，写完就 `/done`） |
| **`/next` 命令不写文件，只装配上下文 + 发任务段** | 大纲是 AI 推演出来的，「用户确认了没」是对话里的事实。命令插在中间会把一次对话拆成两次，还得自己维护一个「等确认」状态 |
| **自动审查用提示级而不是机制级** | pi 没有「工具成功后自动调另一个工具」的钩子。想做成机制级只能把审查塞进 `novel_chapter_write` 内部 —— 那会让一个写文件的工具承担流程编排职责，也会把「写正文」与「跑三个子会话（几分钟）」绑成一次工具调用。**而「忘了」是可被发现的**：状态停在 `drafted` 而不是 `auto_reviewed` |
| **审查报告的「冲突标记」删掉** | 机械层面判不出「两条判定矛盾」（需要语义理解，而引入语义判断正是「不做 LLM 汇总层」要避免的）。实际上发生的是「同一段落有多个不同类别的条目」，那本来就都保留 |
| **合并只去「同一类别同一段落的重复」** | 审查员按类别分工，跨类别的条目本来就不同问题；去重范围放宽等于把第二个视角的意见删了 |
| **应用状态全局化：状态放 `~/.novelmaster/`** | 原先放运行目录（`<cwd>/.novelmaster/` + `<cwd>/novels/`），结果是「换个目录敲 novelmaster 就是另一套书」——而那个惊吓是真实的：用户会以为书丢了。改为全局后，任何目录敲 `novelmaster` 都是同一本。代价是「不同目录装不同书」不再可能，但那位本来就不是需求（单人单本） |
| **测试隔离靠 `NOVELMASTER_HOME` 环境变量** | 状态全局化后测试会互写同一个 `~/.novelmaster/config.json`（并行/顺序都会互相污染）。环境变量覆盖是标准做法（XDG 风格），而且它让“数据放哪”从不可控变成可注入 |
| **去 AI 味用一个子会话，不是三个** | 审查要三个独立视角（单视角会漏），而改写是**一次产出**——三个人各改一遍还得挑一份或合并，只会让「哪一版是最终稿」说不清 |
| **改稿后只重查 F / G（不是完整重跑）** | 完整重跑会让报告里绝大多数条目是重复的（事实层问题第一次报过而用户未处理），新问题反而被埋。判据是**改动的作用域**：去 AI 味只动表达层，F/G 是表达层最容易被改坏的，A–E 不该被碰到 |
| **另配一道机械防线扫专有名词** | 「不该被碰到」不等于「没被碰到」。用正则扫改动段落里的人名 / ID / 数字，能**明确报出越界**，而不靠审查员去猜 |
| **讨论的输入包不含设定条目与人物档案** | 判据与审查不同：审查漏一条会导致一致性事故（而审查员只能看给定的东西），讨论是探索性的，且角色手里有 `read` / `novel_read_index`，需要时自己取 |
| **讨论视角由主会话设计，不写死也不另起 LLM 生成** | 主会话刚与用户聊完，它已经知道「这几条线」指什么；再起一个会话去猜要准得多，也省一次调用 |
| **未产出与创建失败分开处置** | 前者是模型没按格式交付（可容忍，如实标注）；后者是设施起不来（说明环境有问题，继续跑没有意义）。混成一种要么掩盖故障，要么把小事当事故 |
| **编排逻辑把「起会话」做成可注入的 `runRole`** | 不这么做，并发 / 失败处置 / 未产出标记这些逻辑就只能靠手工试；注进去之后它们全部可自动测 |
| **启动 / 安装 / 卸载逻辑都用 Node 写（`scripts/*.mjs`），平台脚本只做壳** | bash 在 Windows 上不可用，而「bash 一份 + PowerShell 一份」是两个副本。Node 是运行时本来就有的依赖，一份实现跨平台。`install.bat` 等壳**必须纯 ASCII**：UTF-8 的 bat 在中文 cmd（GBK 代码页）下会被切碎成错乱命令（实测执行流失控）；GBK 的 bat 在英文系统上又乱码 —— 纯 ASCII 是唯一在任何代码页下都正确解析的写法 |
| **测试不依赖用户全局目录里的外部资源（humanizer skill）** | 测试的判据应该是「本项目的代码逻辑对不对」，不是「用户机器上恰好装了什么」。依赖外部资源会让测试在另一台机器上无故变红；skill 路径与文本做成可注入，测试用假 skill 文件自包含 |

## 2. 与用户原始要求的偏差清单

设计过程中对用户原始描述做的改动，全部列在这里以便复核。

| 用户原话 | 设计 | 原因 |
|----------|------|------|
| `/quit` 退出大纲层 | 改为 `/back` | `/quit` 是 pi 内建「退出程序」，占用它会产生 `/quit:1` 这种后缀化命名 |
| 「技术栈是 TS 命令行 TUI」 | 宿主式扩展，不自研 TUI | 见 `architecture.md`；功能与交互形态不变，省掉重写 pi 已有层的工作量 |
| 「不使用 markdown 语法」 | 只约束正文 txt | 资料层必须结构化，否则审查无据可查 |
| 「创建多个 agent」 | 多个独立 `AgentSession` | pi SDK 无多 agent 概念；独立会话视角不互相污染、成本可控 |
| 「用默认模型」 | 默认读 pi 配置，但提供按用途覆盖 | `deepseek-flash` 写正文质量上限受限；是否换由用户判断，不替他决定 |

## 3. 设计过程中新增、用户未提出的机制

这些都是为了让已有要求真正成立而不得不加的东西。

| 新增 | 为什么必须有 |
|------|--------------|
| `/context` 命令 | 装配器是质量中枢，看不见就调不动，出了问题只能靠猜 |
| `pendingReflow` 闸门 | 用户判断建立在资料可信之上（见 §1） |
| `lastUpdatedChapter` 字段 | 让「某角色久未更新」从靠记性变成可检测 |
| 依据引用校验 | 让「不能凭感觉」从口号变成机制 |
| 章节摘要（每章一个文件） | 「最近 N 章全文 + 更早摘要」策略的必备产物，不是可选优化 |
| 回填报告 `NNN.reflow.md` | 记录每次回填往追加式文件里写了什么，让资料的可信度本身可追溯 |
| 未实现命令也注册 | 见 §1 |
| 写入护栏（拦 write/edit） | 让「LLM 只能通过工具写数据」从提示词建议变成机制。防的是「模型不知道有工具、直接手写 JSON」，而不是防它故意绕过（见 `data.md「写入护栏」`） |
| 写入结果的 diff 摘要 | 「改了什么」可能比「改成功了」有价值得多：用户能据此说「第 3 条别动」 |
| 正文校验的两段式确认 | 「只提示不阻断」要成立，必须有个地方承接用户的确认决定，而工具没有二次交互能力 |
| 正文校验只提示不阻断 | 小说正文里出现 `-` 是合法的（破折号、对话），硬拦会误伤；且用户要亲手编辑这个文件 |

## 4. 踩坑记录

### 4.1 同名命令在多个层面被重复注册（里程碑 1）

**现象**：冒烟测试报 `命令无重复注册 FAIL — 注册了 16 个，去重后 14`。

**根因**：第一版把命令定义写在各层面的列表里（`LAYER_COMMANDS: Record<Layer, LayerCommandSpec[]>`），而 `/brainstorm` 出现在 outline / event / write 三个层面，于是同一个命令被定义并注册了三次。pi 对同名命令的处理是保留全部并加数字后缀 —— 用户会看到 `/brainstorm:1`、`/brainstorm:2`、`/brainstorm:3` 三个坏掉的命令名。

**修复**：拆成两张表。

| 表 | 内容 |
|----|------|
| `COMMANDS` | 命令自身的信息（说明、交付里程碑） |
| `LAYER_COMMAND_ORDER` | 命令出现在哪些层面、按什么顺序显示 |

注册循环遍历 `COMMANDS` 的键，**重复注册在结构上不可能发生**。再用断言把两张表锁在一起（每个命令至少出现在一个层面表；层面表里没有未定义命令名），防止将来手写漂移。

**留下的教训**：这是「同一个事实写在两个地方」的典型代价。修法不是去重，而是让那个事实只有一处来源。

### 4.2 输入拦截层没有存在理由（里程碑 1）

**现象**：设计文档原本安排了 `src/extension/input-router.ts`：在非主菜单层面拦截用户输入、打上层面标记，供 `before_agent_start` 读取。

**根因**：层面本来就是扩展进程内的一个变量（`layers.ts` 的 `currentLayer`）。`before_agent_start` 直接读它就行，不需要把同一个信息先写进输入文本再读出来。那一层增加的只有出错面，没有能力。

**修复**：删除该模块，链路简化为「用户说话 → pi 交给 agent → `before_agent_start` 读 `getLayer()` → 注入层面段」。

**留下的教训**：为了「将来可能需要」先摆一个空壳，代价是现在就要维护它，而它的存在会让人以为流程里有这一步。**需要时再加，而不是先加着。**

### 4.3 章节状态机与层面模式机是两个维度

**踩坑风险**：很容易把「当前层面」和「当前章状态」合成一个枚举（比如 `writing.outlined` 这种组合值）。

**为什么不能合**：层面管「用户在哪个视角」，章状态管「这一章走到哪一步」。用户可以在写作模式下反复进出层面，也可以在任意章状态下去大纲层改大纲 —— 两者正交。合成一个枚举会让状态数变成笛卡尔积，且每次加层面都要重新枚举一遍所有组合。

**已固化的约束**：见 `interaction.md「模式机」`。

### 4.4 泛型 helper 把 typebox 的类型推导推没了（里程碑 2）

**现象**：把枚举 schema 写成 `const literals = (...values) => Type.Union(values.map(Type.Literal))`，
想少写几行；结果 `Static<typeof XSchema>` 推导成 `never`，而报错出现在**使用这些 schema 的对象上**（「Type 'string' is not assignable to type 'never'」），完全看不出根因在 helper 上。

**根因**：泛型 tuple 经过 `.map()` 后字面量信息丢失，返回类型变成 `TLiteral<string>[]`，而 typebox 的 `Static` 对宽泛的 `string` 无法收缩。

**修复**：放弃 helper，枚举 schema 内联手写；用「常量列表 ↔ schema 互锁断言」防止两份内容漂移。
这是本项目第二次用这个手法（第一次是两张命令表）。

**留下的教训**：为了少写几行而引入类型体操，代价是把编译错误从发生地推到了远处的使用处。
`never` 类的报错几乎总是「某个泛型描述丢失了」，而不是使用代码写错了。

### 4.5 typebox 默认允许额外属性（里程碑 2）

**现象**：实测确认 —— `Type.Object({ a: Type.String() })` 对 `{ a: "x", b: 1 }` 的 `Value.Check` 返回 **true**。

**为什么致命**：本项目引入 schema 校验的全部理由就是「JSON 被 LLM 手写会漂移」（字段名变体、漏 `schemaVersion`）。
默认宽松就等于只拦住了「字段完全缺失」，而放过了「字段名写错但多了一个」这类最典型的漂移 —— 后者会静默落盘成脏数据。

**修复**：所有对象（包括工具的参数字典）显式写 `additionalProperties: false`，
集中为 `schema.ts` 导出的 `STRICT`，并在测试里断言「多余字段被拒绝」。

### 4.6 `readJson` 分不清「没这本书」与「书坏了」（里程碑 2）

**现象**：原实现是 `try { JSON.parse(readFileSync(path)) } catch { return null }`。
于是一本被用户手改坏的小说，在启动时表现为「没有打开小说」—— 用户看到的是正常状态，而不是数据损坏。

**根因**：`catch` 把所有错误（`ENOENT` / `EISDIR` / JSON 语法错）归成了一类。
而这三种情况的正确反应完全不同：第一种是常态，后两种是事故。

**修复**：新增 `readJsonFile`：`ENOENT` 返回 null，其余抛错；再往上由 `readDoc` / `openNovelStrict` 转成**带文件路径的**错误文本。

**留下的教训**：`catch` 一个具体的错误类型，而不是 `catch` 一切。
“失败不静默降级”这条原则的第一破坏者，就是那个吞掉所有错误的空 `catch`。

### 4.7 `customTools` 被自己的白名单挡在门外（里程碑 4b）

**现象**：子会话正常起来、跑了 60 秒、输出了很高质量的结构分析，但收集到的产出是空的（**两个角色都是**）。模型在文本末尾明确报告：`Tool submit_brainstorm not found`，可用工具只有内置的四个只读工具。

**根因**：`createAgentSession` 的 `tools` 参数是**白名单**，自定义工具的名字也必须列进去。只传 `customTools` 而不把名字加进 `tools`，它就等于被自己的白名单挡在外面。pi 文档里只有一句话提到这点（`If you pass tools, include each custom or extension tool name you want enabled`），不显眼。

**为什么这个坑特别阴**：它不报任何错。工具「定义了」、会话「跑通了」、模型「认真干活了」，只有产出是空的——而空产出在业务上有一个看似合理的解释（「模型忘了提交」）。第一次看到时我差点去调提示词。

**修复**：`tools: [...内置只读, ...customTools.map(t => t.name)]`。

**留下的教训（比坑本身重要）**：这次失败被业务逻辑**误判**了——它被归入「未产出（模型没按格式交付）」，而真实原因是设施故障。两者的处置完全相反（一个可容忍，一个该中止）。

所以判据不能只是「有没有产出」：未产出的 reason 里现在附上子会话的**最后一段输出**，让「它只是没交」与「它想交而交不上」在结果里可区分。**不嗅字符串**（模型措辞一变就穿），只把它的原话端出来。

### 4.8 Windows 上只读句柄 fsync 报 EPERM（Windows 兼容化）

**现象**：项目宣称支持 Windows，但在 Windows 上跑 `npm test` 全军覆没，首个报错是 `src/data/io.ts` 的 `fsyncSync` 抛 `EPERM`（errno -4048）。

**根因**：`fsyncFile` 用 `openSync(path, "r")` 只读句柄打开临时文件再 fsync。Linux 上对只读句柄 fsync 没问题，Windows 要求句柄有写访问权才能 flush，直接 EPERM。项目一直在 Termux（Linux 内核）上开发，从未在 Windows 上跑过测试，所以一直没暴露。

**修复**：`openSync(path, "r+")`。这些 tmp 文件都是写入函数刚写出来的，一定有写权限。

**留下的教训**：文档里写「支持 Windows」不是事实，除非测试真的在 Windows 上跑过。跨平台声明的验证手段只有一个：在每个声明支持的平台上跑一遍测试。

### 4.9 测试硬依赖用户全局目录里的 humanizer skill（Windows 兼容化）

**现象**：`tests/deai.ts` 断言「能读到 humanizer skill」并检查 skill 正文内容，文件路径写死 `~/.pi/agent/skills/humanizer/SKILL.md`。换一台没装这个 skill 的机器（本次 Windows 机器就是），3 条断言失败，随后的去 AI 味编排测试抛 DataError 中断，尾部 13 条断言根本没跑。

**根因**：测试把「外部资源存在」当成了自己的前提。humanizer skill 是 pi 生态里用户自己安装的资源，不是本项目的资产 —— 测试硬依赖它，等于让测试结果跟着用户机器的安装状态走。

**修复**：skill 路径与文本做成可注入（`readHumanizerSkill(path)` + `DeaiOptions.skillText`），测试用临时假 skill 文本验证「读文件 / 去 frontmatter / 内容断言 / 读不到返回 null / 编排报错」全部逻辑。真实 skill 的存在性仍由运行时校验（读不到即报错，不静默跳过）。

**留下的教训**：测试自包含是硬要求。任何指向 `~/.pi/`、`~/.novelmaster` 或其它用户全局路径的测试断言，都会让测试在另一台机器上无故变红 —— 而「无故变红」的测试很快会被人习惯性忽略，那时真变红也没人看了。

### 4.10 bat 脚本的 UTF-8 编码在中文 cmd 下解析错乱（Windows 兼容化）

**现象**：UTF-8（无 BOM）编码的 `install.bat` 在中文 Windows 的 cmd 下执行，中文提示行全部变成「xx 不是内部或外部命令」（乱码输出），执行流失控 —— 实测甚至意外拉起了一个 TUI 进程，把整条测试拖到超时。

**根因**：cmd 按当前代码页（中文系统为 GBK/936）**逐字节**解析 bat 文件。UTF-8 的中文字节序列被 GBK 解析器切成错乱的命令边界，一条 echo 行被切成多条非法命令。`chcp 65001` 也救不了：它只改变后续输出的解码，bat 文件本身的解析早就在执行它之前用旧代码页开始了。

**修复**：bat 壳只保留纯 ASCII 内容（一行 `node "%~dp0scripts\install.mjs"`），安装 / 卸载逻辑与全部中文提示移到 Node 脚本。纯 ASCII 在任何代码页下都正确解析；老 cmd 里 Node 输出的中文可能显示乱码，但**命令执行不再错乱**。

**留下的教训**：跨平台脚本的编码策略是「逻辑进 Node / Python 等运行时，平台壳纯 ASCII」。在壳里写中文等于把「解析正确性」押在用户终端的代码页上 —— 而代码页是每台机器都不同的东西。

## 5. 已否决的方案（不要重新发明）

下面这些方案在需求打磨阶段被考察并**明确排除**。记下来是为了避免后来者（或后来的会话）重新提一遍。

| 领域 | 方案 | 优点 | 为何否决 |
|------|------|------|----------|
| 上下文策略 | 注入**全部**已写章节全文 | 实现最简单，完全忠实 | 第 50 章时 token 与成本失控，且重点被稀释 —— 不只是贵，还会因为塞太多而让模型抓不住重点 |
| 上下文策略 | **只注入摘要**，不注入原文 | 最省 | 丢失文风、称呼、细节连续性，直接影响下一章质量 |
| 上下文策略 | 大纲 + 事件 + 人物 + 设定 + **最近 N 章全文** + 更早摘要 | 忠实且有界 | ✅ **采纳**（N 默认 5，可配置） |
| 多 agent | 引入**子 agent 委派链路** | 支持多轮交互式辩论 | 复杂度、成本、可调试性都陡增；第一版不值 |
| 多 agent | 多个独立 `AgentSession` + 角色 prompt，父层综合 | 简单、成本可预期、视角互不污染 | ✅ **采纳** |
| 审查依据 | 每次审查时让 AI **现读前文自行判断** | 免维护 | 无法追溯，判定不稳定 —— 直接违背「不能凭感觉」 |
| 审查依据 | 结构化设定集 + 人物档案，报告逐条引用 | 可追溯 | ✅ **采纳** |
| 审查汇总 | 再起一个 LLM 会话做汇总 | 能做语义去重 | 条目已是结构化的，机械合并足够；多一层 LLM 只增加编造风险（见 §1） |
| 审查汇总 | 代码级机械合并 + 依据校验 | 无新增编造风险 | ✅ **采纳** |
| 讨论汇总 | 再起一个 LLM 会话做「共识 / 分歧」的归纳 | 能做语义去重与归纳 | **已否决**：主会话本来就在跟用户对话、本来就有全部上下文，另起一层只会多一份编造风险（与上一条同一理由）。工具把结构化产出交给主会话，归纳由它做 |
| 阶段划分 | 把大纲的阶段**结构化**成一份阶段清单（带 ID），事件用 ID 引用 `stage` | 可机械校验「事件挂在了已定义的阶段上」；排序、分组、查找都不靠语义 | **已否决**：一部小说的阶段数是 3–5 个且很少变，而事件挂错阶段不会导致任何事故（只是显示位置不对）——**审查项里也没有一条依赖阶段的结构化**。代价却是真实的：大纲写入要同步维护阶段清单，多一份可漂移的副本。保持自由文本，与大纲靠语义对齐 |
| 阶段名一致性 | 解析大纲正文提取阶段名，在事件清单里标出「`stage` 不在大纲里」 | 能发现手滑写错阶段名 | **已否决**：提取依赖大纲的区段格式，而格式是用户可改的 —— 一个会误报或漏报的提示比没有提示更糟（用户会以为它可信）。改为在文档里写明约束：**里程碑 8 的 E1（主线脱轨）会用 `event.stage` 去大纲里找阶段目标，所以阶段名应保持一致** |
| 写入护栏 | **禁用 `bash` / `powershell`**，让「只能走工具」在机制上闭合 | 无旁路 | **已否决**（曾实现过，又拆掉）：代价是立刻发生的（AI 不能跑 git / 测试 / 查日志），而它防的是一条模型不会主动走的路径 —— 绕过护栏需要一个明确的、主动绕开的意图。护栏的价值在于把正常路径摆正（见 `data.md「写入护栏」`） |
| 工具暴露 | 按层面动态收窄可见工具（setting 层只给 setting 类工具） | 更贴合「每层只装载该层数据」 | **暂缓**：能降 token，但要处理层面切换时的工具集重算与缓存失效（pi 的工具集变化会触发 prompt 重建）。里程碑 2 先全量注册，等各层面真正定型后再按实际需要收窄 —— 过早收窄会因猜错需要而反复改 |
| 结局判定 | 给审查报告打「质量分」 | 直观 | 成功判据是「用户判断」，工具无权给结论，只能摊开证据 |
