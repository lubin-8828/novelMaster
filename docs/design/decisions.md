# decisions — 关键设计决策与原因

> 父文档：[`DESIGN.md`](../../DESIGN.md)
>
> **本文档是动手前的必读项。** 下面每一条都是已经权衡过的决策；不了解「为什么」就改动，很可能把它退回到已经被否决的形态。

---

## 1. 决策 → 根因

| 决策 | 根因（为什么非这样不可） |
|------|--------------------------|
| **宿主式架构，不自研 TUI** | 价值在数据层 / 上下文装配器 / 审查规则三处，不在终端渲染。pi-tui 只提供零件，不提供「编辑器 + 对话 + 流式 + 会话管理」那一整层；自研等于重写 pi 已有的 80%，还要跟着 pi 升级 |
| **结构化数据只经 custom tools 写入** | JSON 被 LLM 手写必然漂移（字段名变体、漏 `schemaVersion`、数组变对象）。而所有审查依据都建立在这些文件上 —— 依据链是承重墙，结构一坏就断 |
| **追加式与覆盖式分离** | 历史可改 = 依据可伪造。用户之所以敢信审查，是因为它能指着「CH-005 那章发生了这件事」说话；这条记录若能被后续回填悄悄覆盖，整个依据链就烂了 |
| **审查者只读（连改的能力都没有）** | ① 写手自查自己的稿子有确认偏差；② 一旦允许顺手改，「哪一版是被审查过的」就说不清了 —— 而用户的验收对象必须是确定的 |
| **结构化提交（工具参数）而非 JSON 文本** | 模型可以写出一段「看起来像 JSON 的散文」骗过解析器，但骗不过 typebox schema。这直接决定了审查报告能不能被机械汇总与校验 |
| **依据引用可校验** | 不存在的依据 = 幻觉。能自动识别出来，才不会要求用户去人工核对每条引用是否真实 |
| **不做 LLM 汇总层** | 审查条目已经是结构化的，机械合并足够；多一层 LLM 只会引入新的编造风险 —— 而编造正是这套机制要防的东西 |
| **冲突条目两条都保留** | 两个独立视角矛盾这件事本身就是高价值信号；机械取一方会把它抹平。同一条理由也适用于脑暴不投票 |
| **脑暴父层综合、不投票** | 投票式少数服从多数会掩盖真实分歧，而分歧是用户最需要看到的东西 |
| **脑暴必须先有用户给定的方向** | 没有方向的自由发散容易偏离用户思路；用户要的是「在我指的方向上帮我展开」，不是「换一个故事」 |
| **审查在前、去 AI 味在后** | 审查改事实层（对不对），去 AI 味改表达层（像不像人写的）。反了的话，去 AI 味改过的句子再被判有问题，那一轮改写白做 |
| **humanizer 显式注入而非 skill 自主加载** | 「做没做去 AI 味」必须是代码事实，不能是模型的心情。skill 自主加载是模型驱动的 —— 这章想不起来加载就静默跳过了，而用户从结果上分辨不出 |
| **检查清单写死 28 项，不让 AI 自由审** | 成功判据是「用户判断」，所以 AI 唯一能做的是不许自由发挥。跑同一份清单，用户才能横向对比、才能发现清单缺了什么 |
| **依据引用取并集不取交集** | 两种错误的代价不对称：多喂一条人物档案只是多点 token，漏一条会导致一致性事故，而一致性事故要靠用户逐条审出来 |
| **失败不静默降级** | 用户判断是最终判据，假信号会让整套设计失效 |
| **`state.json` 是唯一进度真相** | 多源真相迟早不一致，而不一致时没有任何依据可以裁决哪个是对的 |
| **`/done` 有准入闸门（未回填不许结章）** | 成功判据由用户主观判断 → AI 必须摊开证据而非给结论 → 用户判断建立在资料层可信之上。资料一失真，判断就建立在假信息上 |
| **正文文件里只有正文** | 用户要亲手编辑 txt；任何混进正文的元数据都会在编辑时被误删或误改 |
| **原计划的输入拦截层被删除** | 层面本就是进程内变量，`before_agent_start` 直接读即可。把同一个信息先写进输入文本再读出来是纯粹的中间环节，只增加出错面 |
| **命令表拆成两张** | 否则跨层命令被重复注册、被 pi 后缀化成 `/brainstorm:1`（见「踩坑记录」） |
| **未实现的命令也注册** | 只在 `/help` 列出却不注册，敲下去会被当成普通文本交给 AI —— 用户以为执行了命令，实际是 AI 在揣摩他的意思 |
| **无构建步骤（Node 原生类型剥离）** | 少一层构建就少一层「源码与运行物不一致」的可能，也少一套「改完忘了重新构建」的失败模式 |
| **不引入数据库 / ORM / TUI 框架** | 单机单用户，JSON + txt 足够，且用户明确要求资料可读可改 |

## 2. 与用户原始要求的偏差清单

设计过程中对用户原始描述做的改动，全部列在这里以便复核。

| 用户原话 | 设计 | 原因 |
|----------|------|------|
| `/quit` 退出大纲层 | 改为 `/back` | `/quit` 是 pi 内建「退出程序」，占用它会产生 `/quit:1` 这种后缀化命名 |
| 「技术栈是 TS 命令行 TUI」 | 宿主式扩展，不自研 TUI | 见 `architecture.md`；功能与交互形态不变，省掉重写 pi 已有层的工作量 |
| 「不使用 markdown 语法」 | 只约束正文 txt | 资料层必须结构化，否则审查无据可查 |
| 「创建多个 agent」 | 多个独立 `AgentSession` | pi SDK 无多 agent 概念；独立会话视角不互相污染、成本可控 |
| 「用默认模型」 | 默认读 pi 配置，但提供按用途覆盖 | `deepseek-flash` 写正文质量上限受限；是否换由用户判断，不替他决定 |

## 3. 设计过程中新增、用户未提出的机制

这些都是为了让已有要求真正成立而不得不加的东西。

| 新增 | 为什么必须有 |
|------|--------------|
| `/context` 命令 | 装配器是质量中枢，看不见就调不动，出了问题只能靠猜 |
| `pendingReflow` 闸门 | 用户判断建立在资料可信之上（见 §1） |
| `lastUpdatedChapter` 字段 | 让「某角色久未更新」从靠记性变成可检测 |
| 依据引用校验 | 让「不能凭感觉」从口号变成机制 |
| 章节摘要（每章一个文件） | 「最近 N 章全文 + 更早摘要」策略的必备产物，不是可选优化 |
| 回填报告 `NNN.reflow.md` | 记录每次回填往追加式文件里写了什么，让资料的可信度本身可追溯 |
| 未实现命令也注册 | 见 §1 |
| 正文校验只提示不阻断 | 小说正文里出现 `-` 是合法的（破折号、对话），硬拦会误伤；且用户要亲手编辑这个文件 |

## 4. 踩坑记录

### 4.1 同名命令在多个层面被重复注册（里程碑 1）

**现象**：冒烟测试报 `命令无重复注册 FAIL — 注册了 16 个，去重后 14`。

**根因**：第一版把命令定义写在各层面的列表里（`LAYER_COMMANDS: Record<Layer, LayerCommandSpec[]>`），而 `/brainstorm` 出现在 outline / event / write 三个层面，于是同一个命令被定义并注册了三次。pi 对同名命令的处理是保留全部并加数字后缀 —— 用户会看到 `/brainstorm:1`、`/brainstorm:2`、`/brainstorm:3` 三个坏掉的命令名。

**修复**：拆成两张表。

| 表 | 内容 |
|----|------|
| `COMMANDS` | 命令自身的信息（说明、交付里程碑） |
| `LAYER_COMMAND_ORDER` | 命令出现在哪些层面、按什么顺序显示 |

注册循环遍历 `COMMANDS` 的键，**重复注册在结构上不可能发生**。再用断言把两张表锁在一起（每个命令至少出现在一个层面表；层面表里没有未定义命令名），防止将来手写漂移。

**留下的教训**：这是「同一个事实写在两个地方」的典型代价。修法不是去重，而是让那个事实只有一处来源。

### 4.2 输入拦截层没有存在理由（里程碑 1）

**现象**：设计文档原本安排了 `src/extension/input-router.ts`：在非主菜单层面拦截用户输入、打上层面标记，供 `before_agent_start` 读取。

**根因**：层面本来就是扩展进程内的一个变量（`layers.ts` 的 `currentLayer`）。`before_agent_start` 直接读它就行，不需要把同一个信息先写进输入文本再读出来。那一层增加的只有出错面，没有能力。

**修复**：删除该模块，链路简化为「用户说话 → pi 交给 agent → `before_agent_start` 读 `getLayer()` → 注入层面段」。

**留下的教训**：为了「将来可能需要」先摆一个空壳，代价是现在就要维护它，而它的存在会让人以为流程里有这一步。**需要时再加，而不是先加着。**

### 4.3 章节状态机与层面模式机是两个维度

**踩坑风险**：很容易把「当前层面」和「当前章状态」合成一个枚举（比如 `writing.outlined` 这种组合值）。

**为什么不能合**：层面管「用户在哪个视角」，章状态管「这一章走到哪一步」。用户可以在写作模式下反复进出层面，也可以在任意章状态下去大纲层改大纲 —— 两者正交。合成一个枚举会让状态数变成笛卡尔积，且每次加层面都要重新枚举一遍所有组合。

**已固化的约束**：见 `interaction.md「模式机」`。

## 5. 已否决的方案（不要重新发明）

下面这些方案在需求打磨阶段被考察并**明确排除**。记下来是为了避免后来者（或后来的会话）重新提一遍。

| 领域 | 方案 | 优点 | 为何否决 |
|------|------|------|----------|
| 上下文策略 | 注入**全部**已写章节全文 | 实现最简单，完全忠实 | 第 50 章时 token 与成本失控，且重点被稀释 —— 不只是贵，还会因为塞太多而让模型抓不住重点 |
| 上下文策略 | **只注入摘要**，不注入原文 | 最省 | 丢失文风、称呼、细节连续性，直接影响下一章质量 |
| 上下文策略 | 大纲 + 事件 + 人物 + 设定 + **最近 N 章全文** + 更早摘要 | 忠实且有界 | ✅ **采纳**（N 默认 5，可配置） |
| 多 agent | 引入**子 agent 委派链路** | 支持多轮交互式辩论 | 复杂度、成本、可调试性都陡增；第一版不值 |
| 多 agent | 多个独立 `AgentSession` + 角色 prompt，父层综合 | 简单、成本可预期、视角互不污染 | ✅ **采纳** |
| 审查依据 | 每次审查时让 AI **现读前文自行判断** | 免维护 | 无法追溯，判定不稳定 —— 直接违背「不能凭感觉」 |
| 审查依据 | 结构化设定集 + 人物档案，报告逐条引用 | 可追溯 | ✅ **采纳** |
| 审查汇总 | 再起一个 LLM 会话做汇总 | 能做语义去重 | 条目已是结构化的，机械合并足够；多一层 LLM 只增加编造风险（见 §1） |
| 审查汇总 | 代码级机械合并 + 依据校验 | 无新增编造风险 | ✅ **采纳** |
| 结局判定 | 给审查报告打「质量分」 | 直观 | 成功判据是「用户判断」，工具无权给结论，只能摊开证据 |
