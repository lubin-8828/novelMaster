## 1. 错误处理与失败模式

| 情形 | 行为 |
|------|------|
| JSON schema 校验失败 | 拒绝写入，返回错误给 LLM 让它修正；连续 3 次失败则中止并报给用户 |
| 追加式写入检测到原有行丢失 | 拒绝写入并报警（数据损坏级信号） |
| 追加式写入锚点（如 `## 关键事件时间轴`）不存在 | 拒绝写入，**不自动补区段**。区段消失说明文件结构已被破坏，静默补一个空区段会把这个事实藏起来 |
| 工具引用的 ID 不存在 | 拒绝写入，并列出最接近的候选 ID（`C-001` 写成 `C-01` 是最常见的错误形态） |
| 同一工具连续 3 次 schema 校验失败 | 中止并报给用户。连续失败通常是模型理解错了数据结构，第 4 次不会更好 |
| LLM 试图用 `write`/`edit` 写小说根下的文件 | 阻断，告知改用对应的 `novel_*` 工具（见 `data.md「写入护栏」`） |
| 子会话创建失败 | 中止该子任务并报错；**不降级为单会话审查**（否则「3 个独立视角」变成 1 个，用户以为是 3 个） |
| 子会话超时 | 中止并报错，**不静默用部分结果** |
| `submit_findings` 未被调用 | 该审查员记为「未产出」，报告里明示；不假装它审过了 |
| 依据校验全部失败 | 报告标注「本次审查依据普遍无效」，建议用户检查数据层 |
| 模型调用失败 / 重试耗尽 | pi 自身处理重试；扩展层只在 `agent_end` 后检查是否有正文产出 |
| 用户在生成正文中途 Ctrl+C | 状态停在 `outlined`，不落盘半截正文 |
| `/done` 准入不满足 | 拒绝，逐条列出缺什么 |
| 正文写入命中 markdown 标记 | 提示用户确认，不阻断 |
| 小说根目录不存在 / 不是合法小说 | 启动时检测（`isNovelRoot`），提示初始化 |
| `meta.json` 已存在时执行 `/init` | 拒绝并报错。**覆盖一本小说等于抹掉用户全部创作**，不能有「手滑」入口 |
| 核心想法为空时执行 `/init` | 拒绝建书。premise 是一切推断的根，没有它后面全是悬空 |

### 1.1 总原则：失败时绝不静默降级

宁可报错停下，也不要让用户以为某一步做了、其实没做。

**根因**：用户判断是整套流程的最终判据。建立在假信号上的判断会让整套设计失效 —— 用户以为审查跑过了、资料回填了、上下文清空了，于是基于这些前提做决策，而实际上都没有发生。

同一条原则的两个具体落点：

- **未实现的命令也要注册**，敲下去明确提示「计划在里程碑 N 交付」，而不是被当成普通文本交给 AI（见 `interaction.md「命令名的唯一来源与两张表」`）。
- **占位资源不假装可用**：子会话起不来就报错，不退化成单会话。

## 2. 验收清单

### 2.1 自动化（`npm test`，不启动 TUI，共 771 项断言）

按**测试文件**分成五组，而不是按里程碑：断言会随里程碑继续长（里程碑 3 就给数据层与工具层补了断言），按里程碑分会变成「同一组里混着不同时期写的东西」，而实际能跑的是文件。

| 组 | 文件 | 项数 |
|----|------|------|
| 一、装配、层面与文档 | `tests/smoke.ts` | 134 |
| 二、层面装载与写作流程 | `tests/layers.ts` | 95 |
| 三、数据层 | `tests/data.ts` | 200 |
| 四、工具层与护栏 | `tests/tools.ts` | 80 |
| 五、多 agent 讨论 | `tests/brainstorm.ts` | 55 |
| 六、上下文装配器 | `tests/context.ts` | 74 |
| 七、审查引擎 | `tests/report.ts` | 87 |
| 八、去 AI 味引擎 | `tests/deai.ts` | 45 |

分组名与项数**不是手写的**，是从 `npm test` 末尾打印的计数抄回来的 —— 两者不一致时以测试输出为准。表格按场景归类，一个场景可能对应多条断言（如「枚举互锁」覆盖 8 个枚举），所以行数少于项数是正常的。

| 场景 | 预期 |
|------|------|
| 合法对象 | `isValid` 通过 |

**ID 分配（9 项）**

| 场景 | 预期 |
|------|------|
| 空集合 | `S-001` |

**写入差异（23 项）**

| 场景 | 预期 |
|------|------|
| `diffFields`：新建（`before` 为 `undefined`） | 不产生 diff |
| 未变字段 | 不入列 |
| `boolean` / 数组 / `null` | 分别渲染为「是／否」／顿号连接／「（无）」 |
| 空数组 | 显式为「（空）」 |
| 长字符串（> 80 字） | 只报长度，不贴全文 |
| 新建时 `changes` | 为空（没有 diff 可报） |
| 更新 | 列出变化字段，带 `before → after` |
| 传入相同值 | `changes` 为空 —— 「没有实际变化」是**可被机器判定**的，不靠模型自觉 |
| 详述变化 | 被捕获，且只报长度 |
| `tags` / `deprecated` | 可写入；废止的条目**仍在索引里**（不删除）；可改回 `false` |
| 人物更新 | diff 同时覆盖顶层字段与 `static` 子字段 |

## 3. 已知限制

| 限制 | 说明 | 影响 |
|------|------|------|
| 同时只能打开一本小说 | `config.json` 只有一个 `novelRoot` | v1 明确非目标；目录结构已为 v2 预留 |
| 无构建步骤 → 不能用 `enum`/`namespace`/构造器参数属性 | Node 类型剥离不做代码生成 | 写这些语法会在运行时直接报错 |
| 护栏可被 shell 绕过 | 只拦 `write`/`edit` 写小说根；用 `bash` 手写 JSON 能绕过去 | **刻意保留**：关掉 shell 的代价大于收益，且绕过需要模型主动绕开一个明确的拒绝提示（见 `data.md「写入护栏」`） |
| 命令必须以 `/` 开头 | 宿主是 pi，输入框是 pi 的编辑器 | 无法做全屏自绘面板 |
| 无热更新 | 扩展是 `extensionFactories` 内联注册的，`/reload` 不重载它 | 改完 `src/` 必须重启进程 |
| 段落编号依赖空行分段 | `chapter#012:para7` 的校验是「段落数 ≥ 7」（尽力而为） | 用户手工编辑打乱空行后，段落引用可能偏移 |
| 里程碑 1 尚无写入工具限制 | 已在里程碑 2 关闭：写入护栏拦 `write`/`edit` 写小说根，错误文本导向 `novel_*` 工具 | 已解决 |
| 默认模型 `deepseek-flash` 写正文质量上限受限 | 见 `ai.md「模型选择」` | 用户可把 `draft` 换成强模型 |

**实际输出样例**

```
本章上下文包（第 003 章）—— 9 段，共约 1042 tokens（1589 字）

   1. meta             约    88 tokens（     91 字）  meta.json
   2. 主线大纲         约    50 tokens（     74 字）  outline.md
   3. 设定             约   162 tokens（    271 字）  setting/index.json 等 3 个
   4. 当前事件（E-001） 约   112 tokens（    161 字）  events/E-001.md
   5. 相关人物         约    94 tokens（    194 字）  characters/C-001.md 等 2 个
   6. 相关关系         约    18 tokens（     18 字）  （无来源）
   7. 最近 5 章正文（实际 2 章） 约 472 tokens（673 字）  chapters/001.txt 等 2 个
   8. 更早章节摘要     约     9 tokens（      9 字）  （无来源）
   9. 第 3 章大纲      约    37 tokens（     98 字）  chapters/003.outline.md
```

**三个设计决定**

| 决定 | 理由 |
|------|------|
| token 估算用 `CJK × 1 + 其他 ÷ 4`，**不用 pi 的 `estimateTokens`** | pi 的公式是 `字符数 ÷ 4`（英文导向），对中文会把 1 汉字算成 0.25 token —— **低估 4 倍**，而低估让人以为自己很宽裕 |
| 空段**保留**（内容写「（无…）」） | 段号稳定，`/context` 才能把「第 4 段是空的」这个信号显示出来。过滤掉空段会把「没有主事件」变成「少了一行」，而这两者对用户的含义完全不同 |
| `/context` **不做全屏展开视图** | 每段内容本来就来自磁盘上的文件，真要逐字看直接 `read` 那个文件即可。参数式单段展开足够覆盖「想看完整」的需求；为它建一套可交互界面是把预算花在已经有现成手段的地方 |

**一处主动修的误导**

第 7 段的标题原本写死「最近 N 章正文」，但实际注入多少章取决于书里写了多少 —— 书只写了 2 章时，标题说「最近 5 章」会让用户按 5 章的体量算账，**误判 2.5 倍**。已改为「最近 5 章正文（实际 2 章）」。

这是本项目的一条通用教训：**凡是「配置值」与「实际发生值」可能不一致的地方，都要把实际值一并端出来**。同一个形状的还有「未产出」的 reason（见 4.7）。

给一本书（有 meta / 大纲 / 两条设定 / 两个人 / 一条关系 / 一个事件 / 第 1 章已确认的大纲），装配出约千 token 的上下文包，让它写 250–350 字：

> 周砚翻了两页值班本，推回去。「记下来，别报。明天的数据链要对总部交一次。」
> 李明没接话。四十七分钟后，屏幕上又立起一道峰。他按了保存，把值班记录里「异常」那一栏空着。

它用上了上下文里的具体设定（S-002 的「周期精确到毫秒」变成台词里的「四十六分五十三秒」），把大纲里的「李明决定先不报」落成一个动作（把「异常」栏空着），人物性格也对（周砚务实）。

**更强的信号：模型守规则**

在另一个只给只读工具的测试环境里，它**拒绝写正文**，理由是读到 `chapterStatus: "not_started"`、确认记录为空，所以「缺的是你那一票」。落盘失败时它也没绕过：

> 我没有把正文落盘。按照「状态只能靠工具改」的规则，我不会在对话里口头宣告它已经落盘，也不会绕过写入函数直接拼文件（那会跳过正文校验、ID 分配与操作留痕）。

这说明规则写进了模型的行为里，而不只是文档里。

**一处连带修复（属于 4b 的缺陷）**

发现 `novel_*` 工具靠 `openNovelStrict(ctx.cwd)` 读 `.novelmaster/config.json` 定位小说，而讨论子会话的 `cwd` 被设成了**小说根**（那里没有 config.json）—— 于是子会话里**所有 `novel_*` 工具都会报「没有打开小说」**，而 4b 宣称的「角色需要资料时自己查」实际上是坏的。已修：子会话 cwd 改为主会话 cwd，小说根路径写进基线文本。加了一条断言锁住它（`runner 拿到的是主会话 cwd，不是小说根`）。

**这个缺陷的教训与 4.7 是同一个**：子会话里的工具失败不会报错到主会话，只会让模型「以为没有工具可用」—— **一个静默失效的能力比没有这个能力更坏，因为它会在文档里被当成已有能力写下去**（我在 4b 就这么写了）。

**已验证**

2. `npm test` 全过：**709 项断言**（比里程碑 7 多 87 项）。

**真实审查的效果（造了一章故意埋问题的正文）**

| 埋的问题 | 结果 |
|----------|------|
| 「三级异能探测器」（设定未确立） | ✅ **blocking** A2，依据 `setting#S-001` / `S-002` / `chapter#001` / `meta#pov` |

**最说明问题的一条**：审查员为「关系变化未留痕」引用了 `relation#R-000` —— 一个不存在的 ID。依据校验当场抓住：

```
### [C3] ⚠️ 依据无效 关系变化未留痕
- **依据**：`relation#R-000` ← **该引用不存在或不可用**
- **备注**：依据引用无效（relation#R-000），可能是编造
```

**AI 编了一个 ID，机械校验把它降级了。** 这就是「不能凭感觉」与「有据可查」从口号变成机制的样子。

**真实运行暴露并修掉的两处**

| 问题 | 处理 |
|------|------|
| 逻辑叙事审查员 180 秒超时（它一人负责 D·E·F·G 四类 14 项，任务最重） | 超时提到 300 秒。**宁等一会儿也不要让四类静默丢失** |
| 同一审查员对同一段重复提交，合并后出现两段逐字几乎相同的内容 | 合并时按现象文本判相似，基本相同的**不并列**（那是噪声，不是第二个视角） |

**一个主动做的修正**

`pipeline.md` 原本要求「冲突条目标 `conflict: true`」。**已删除** —— 机械层面判不出「两条判定矛盾」（那需要语义理解，而引入语义判断正是「不做 LLM 汇总层」要避免的）。实际发生的是「同一段落有多个不同类别的条目」，那本来就都保留。去重范围故意取窄：只去「同一类别同一段落」。

**「自动审查」是提示级的，这一点必须说清**

pi 没有「工具成功后自动调另一个工具」的钩子。所以「自动」落在两处：`novel_chapter_write` 的返回文本要求接着调 `novel_review`，以及写作层规则。**如果模型忘了调，审查就不发生** —— 但用户看得出来：状态会停在 `drafted`（「正文已生成」）而不是 `auto_reviewed`（「已审查」）。**「忘了」是可被发现的，不是静默的**，所以这个取舍可接受。

### 4.12 里程碑 9 · 去 AI 味引擎（2026-09-22 已交付）

**落地的东西**

| 文件 | 作用 |
|------|------|
| `src/ai/deai/skill.ts` | humanizer skill 的**显式注入**（读文件，不让模型自主加载） |
| `src/ai/deai/scope.ts` | 机械范围检查（专有名词 / 数字有没有被增删） |
| `src/ai/deai/report.ts` | `NNN.deai.md` 渲染（命中清单 / 范围检查 / 改前 / 改后） |
| `src/ai/deai/index.ts` | 编排：一个改写子会话 + 落盘 + 触发复查 |
| `src/tools/deai.ts` | `novel_deai` 工具 |
| `tests/deai.ts` | 44 项断言 |
| `src/data/state.ts` | 新增 `advanceStatus`（每次重新读盘）与 `startNextChapter` |

**已验证**

1. `npx tsc --noEmit` 无错。
2. `npm test` 全过：**771 项断言**（比里程碑 8 多 62 项）。
3. TUI 正常启动。

**三个设计决定**

| 决定 | 理由 |
|------|------|
| **一个子会话，不是三个** | 审查要三个独立视角（单视角会漏），而改写是**一次产出** —— 三个人各改一遍还得挑一份或合并，只会让「哪一版是最终稿」说不清 |
| **子会话仍只读，落盘由主流程做** | 不让几千字正文过一次 LLM 的手 —— 转抄即改写 |
| **改稿后只重查 F / G，另配一道机械防线** | 完整重跑会让报告里绝大多数条目是重复的（事实层问题第一次报过而用户未处理），新问题反而被埋。而「去 AI 味越界改事实」用正则扫专有名词与数字来兜 —— 它能**明确报出越界**，不靠审查员去猜 |

**一处主动修的误导**（与里程碑 6 同形）

`advanceStatus` 每次都**重新读盘**判断当前状态，而不是用调用方手里的快照。原因：一次工具调用可能连推两步（`auto_reviewed → deai_done → awaiting_user_review`），拿旧快照判断会把第二步挡掉 —— 而那种失败的形式是「状态没推进」这种很难归因的现象。

**真实改写验证**

造了一段典型的 AI 味正文（not-X-but-Y、强制三段式、破折号、舞台式引子），真跑一次改写：

| 改前 | 改后 |
|------|------|
| 这不是一次意外，而是一次必然。 | 他在等这一刻，现在它到了，算不上意外。 |
| 他不是一个会放弃的人。他是一个会等待的人。 | 他不放弃。他会等下去。 |
| 这不是噪音。这是语言。 | 是语言。 |
| 他停住了——不是因为害怕，而是因为理解。 | 他停住。他明白： |

命中 5 处（§1 × 3、§8、§3+§2），**事实层完整保留**（「四十七分钟」「李明」都在），文风也向第 1 章的样本靠（短句、不解释）。

**这次真实运行暴露并修掉的一处误报**：范围检查把「这不是**一**次意外」「**一**旦听懂」里的「一」当成了数字，一段改稿里误报 3 次。已排除单字「一」—— **一个总在误报的检查等于没有检查**，用户会很快学会忽略它，那时真正的越界也一起被忽略。

### 4.13 里程碑 10 · 回填与 `/done`（2026-09-22 已交付）

**落地的东西**

| 位置 | 作用 |
|------|------|
| `/done` 命令 | 闸门校验（**逐条列出缺什么**）→ `accepted` → `ctx.newSession()` 清空 → 提示 `/next` |
| `startNextChapter`（`data/state.ts`） | 从 `accepted` 推进章号 + `not_started` + **清 `currentEventId`** |
| 写作层规则 | 回填的九步顺序、`pendingReflow` 的两个位置 |

**回填为什么不做成一个工具**：11 步里 9 步都要判断（谁出场、什么算关键事件、关系变没变）。塞进一个工具意味着要么让工具去调 LLM（那是另一个会话），要么让 LLM 把全部信息在一大个参数里给我（那是在参数里编）。**逐条调现有工具**才是对的形状：每步产出都能被用户看见、被日志记录。

**下一章在 `/next` 时推进，不在 `/done` 时推进**：`/done` 之后用户可能今天就停下了 —— 那时状态停在 `accepted` 是对的（「第 N 章已结章」与「第 N+1 章开始了吗」是两件事）。

### 4.14 里程碑 11 · `/brainstorm` 命令入口（2026-09-22 已交付）

设施（编排、子会话、`submit_brainstorm`）已在 4b 交付，这里只补命令入口：`/brainstorm <方向>`。

**命令只做两件事**：校验用户**给了方向**（硬约束：没有方向不启动，否则容易偏离用户思路），以及把「设计视角」交给主会话 —— 它刚跟用户聊过，比命令更知道「这几条线」指什么。

**结语**：至此 11 个里程碑全部交付，`npm test` 771 项断言全过。主链路已完整：

```
/init → /outline → /event → /write → /next → 生成正文 → 审查 → 去 AI 味
  → 用户验收 → 回填 → /done → 清空上下文 → 下一章
```
